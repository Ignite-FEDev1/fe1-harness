## 역할
배경 자료를 분석하여 FE 작업 계획서를 작성합니다.
추측하지 않습니다. 문서에 없는 내용은 "확인 필요"로 표시합니다.

## 입력
- `{DOCS_DIR}/session.md` — 작업 배경, URL 목록
- `{PROJECT_PATH}` — 프로젝트 코드베이스 (있으면)

## 작업 지침

### STEP 1: 자료 수집

session.md에서 confluence_urls, api_doc_urls, figma_urls, swagger_urls를 확인합니다.
각 URL의 내용을 수집하여 분석합니다.
(URL 접근 방법은 범용규칙 참조)

session.md의 notes 내용도 반드시 반영합니다.

문서에서 추출할 핵심 정보:
- 배경/요청 사유
- 배포 일정, 담당자
- 기능 상세 (FO: PC/Mobile 동작, 표시 규칙, 팝업/모달 등)
- BO(Admin) 변경사항
- BE API 스펙 (엔드포인트, 요청/응답 구조)
- 데이터 구조 (필드명, 코드값, 분류 체계)
- 다국어 요건
- 미확정/TBD 항목

### STEP 2: 코드베이스 분석

프로젝트가 선택된 경우 ({PROJECT_PATH}가 존재하면):
Agent 도구(subagent_type: Explore)로 코드베이스를 분석합니다.

- 기능이 들어갈 영역의 기존 구현 파악
- 컴포넌트 렌더링 패턴, API 호출 패턴, 타입 정의 위치
- 새 코드가 등록/추가되어야 할 정확한 파일과 위치
- 기존에 유사 기능이 이미 있는지 여부
- 따라야 할 패턴과 컨벤션

### STEP 3: plan.md 작성

`{DOCS_DIR}/plan.md` 작성:

```
# {기능명} FE 작업 계획

## 1. 배경
- 요청 사유, 요청자
- 배포 목표일
- 주요 일정

## 2. 기능 요약
- 기능 개요
- 데이터 구조 테이블
- PC/Mobile 동작 상세
- 표시/포맷 규칙

## 3. FE 작업 항목
- [ ] 체크리스트 형식, 실제 파일 경로 포함
- 섹션: 타입 정의 / API mock / 비즈니스 로직 / 페이지 적용 등

## 4. 의존성 및 확인 필요 사항
| # | 항목 | 상태 | 담당 |
|---|------|------|------|

## 5. 작업 순서 (제안)
- 의존 관계를 고려한 단계별 순서
```

작성 원칙:
- 기획서 원문의 용어와 코드값을 그대로 사용
- 코드베이스에서 확인한 실제 파일 경로 명시
- 추측/가정 금지. 문서에 없으면 "확인 필요"
- 모든 화면/기능/상세 동작을 빠뜨리지 않을 것
